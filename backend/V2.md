# API v2: movimientos, bolsillos y avisos de cambios

Implementa persistencia normalizada, importación/lectura, creación/edición/eliminación de movimientos, operaciones de bolsillos, recibos de idempotencia y notificaciones SignalR mediante una outbox. Está desactivada por defecto. Falta conectar los clientes. No se ha migrado ninguna cuenta real. Los endpoints y reglas de edición, eliminación y bolsillos se detallan en [operaciones financieras](LIFECYCLE.md).

## Tablas y migración

`Financia.Api/Persistence/` contiene `NormalizedFinanceDb`, las entidades y las migraciones `20261113000100_InitialNormalized` y `20261113000200_MovementCommands`. Se crean `finance_accounts`, `pockets`, `movements`, `command_receipts` y `finance_outbox` en el esquema PostgreSQL `financia`, fuera de `public`. El esquema debe permanecer fuera de los esquemas expuestos por la Data API. Las credenciales de base de datos pertenecen al backend; los clientes solo usan tokens de usuario.

Las claves de bolsillos y movimientos incluyen el usuario. Se mantienen IDs originales y dos decimales de precisión. La tabla `Documents` se consulta para importar el historial del servidor, pero no forma parte de las migraciones v2. El historial de migraciones v2 usa una tabla independiente `__FinanciaV2MigrationsHistory`.

SQLite permite las pruebas locales. PostgreSQL necesita además validación de integración en un servidor real antes del despliegue: las pruebas de generación SQL no sustituyen esa comprobación.

## Ejecutar en una base aislada

Desde la raíz, para una copia de desarrollo nueva, configura una ruta distinta de tu base habitual:

```powershell
$env:ConnectionStrings__Postgres = ''
$env:ConnectionStrings__Sqlite = 'Data Source=financia-v2-dev.db'
$env:FinanceV2__Enabled = 'true'
npm run api:start
```

En desarrollo, se inicializa primero la tabla v1 y se aplican después las migraciones v2. En producción las migraciones son explícitas. En una base nueva inicializa primero v1 con `npm run api:start -- -- --initialize-database`; después, con la bandera v2 activa, ejecuta `npm run api:start -- -- --migrate-v2`. En una base que ya contiene `Documents`, basta el segundo comando. Estos comandos actúan contra la conexión configurada: probar siempre primero con una copia aislada.

La bandera es para introducir esta etapa en un entorno controlado. Mantén todas las instancias con la misma configuración y detén instancias antiguas antes de importar. Si desactivas v2 después de importar cuentas, los endpoints v2 dejan de estar disponibles pero v1 sigue bloqueando esas cuentas al detectar las tablas normalizadas. La reversión requiere reconciliar datos, no cambiar la bandera.

No importes una cuenta utilizada por la app actual hasta que su cliente v2 esté disponible: tras importar, los endpoints v1 devuelven 409 para esa cuenta.

## Autenticación y endpoints

Usan el mismo Bearer token de Supabase ya validado por la API. El usuario siempre se obtiene de la sesión. No hay un parámetro para elegir otro propietario.

- `GET /api/v2/finances`: devuelve `{ revision: "0", snapshot: { version: 2, transactions: [], pockets: [] } }` si no se ha importado la cuenta. Después de importar, la revisión inicial es `"1"`.
- `POST /api/v2/imports/legacy`: importación atómica y explícita. Requiere `Idempotency-Key` (máximo 128 caracteres) y `expectedRevision: "0"`.

Si el usuario ya tiene un historial v1 en el servidor, consulta su revisión con `GET /api/finances` y envía solo:

```json
{ "expectedRevision": "0", "legacyRevision": "1" }
```

El backend toma el snapshot directamente de `Documents`; no lo sustituye por uno enviado por el cliente. Una revisión antigua produce 409. Se conserva el JSON original y su revisión.

Si no existe historial en el servidor, se permite una importación local explícita:

```json
{
  "expectedRevision": "0",
  "snapshot": {
    "version": 1,
    "transactions": [
      { "id": "local-1", "currency": "DOP", "amount": 1250.50, "type": "ingreso", "category": "salario", "date": "2026-11-01T12:00:00Z" }
    ],
    "pockets": []
  }
}
```

Antes de usar este camino, el cliente debe verificar y mostrar a qué cuenta pertenecen los datos locales. El servidor solo puede asignarlos al usuario autenticado; no puede demostrar a quién pertenecía un archivo local.

Repetir la misma solicitud con la misma clave devuelve el resultado original de la importación, incluso si después se crearon nuevos movimientos; usar otra clave en una cuenta importada o reutilizar la clave con otro contenido produce 409. El recibo de importación se conserva en `finance_accounts`. Las cuentas importadas por la primera versión se completan con esa respuesta antes de aceptar su primera escritura nueva.

Los montos de la **respuesta v2** son cadenas decimales (`"1250.50"`), y las versiones y revisiones son cadenas enteras. La entrada legacy mantiene números por compatibilidad. Las fechas deben tener zona horaria explícita y se normalizan a UTC.

Se conservan los saldos existentes sin recalcularlos. Los bolsillos admiten el `color` local opcional. Las referencias a bolsillos históricos ausentes se rechazan con 400 y una lista `movementIds`; requieren resolver la representación histórica antes de importar. No se descarta ni reclasifica el historial.

400 indica datos inválidos, 401 sesión inválida, 409 conflicto/revisión antigua. Los fallos de concurrencia devuelven 409 para recargar y reintentar. Importación y escrituras v1 usan transacciones serializables cuando v2 está activa para evitar que ambas fuentes diverjan.

## Crear ingresos y gastos

`POST /api/v2/movements` requiere Bearer token, una cuenta inicializada/importada y `Idempotency-Key` nueva. Para una cuenta nueva, inicializa explícitamente un snapshot vacío mediante el endpoint de importación; no se inicializa una cuenta silenciosamente al crear un gasto.

```json
{
  "id": "movimiento-local-1",
  "currency": "DOP",
  "amount": "1250.50",
  "type": "ingreso",
  "category": "salario",
  "date": "2026-11-13T08:00:00-04:00",
  "note": "Pago recibido"
}
```

La respuesta es 201 con `{ revision: "2", movement: { ... } }`; el movimiento incluye su versión `"1"` y fecha UTC. `amount` debe ser una cadena decimal positiva con punto y hasta dos decimales, sin separador de miles; moneda y categorías conservan los valores existentes. No admite `userId`, `pocketId` ni campos desconocidos. La categoría `ahorro` está reservada para los comandos transaccionales de bolsillos.

El servidor asigna la propiedad desde la sesión. Guarda movimiento, aumento de revisión, recibo y evento en la misma transacción. Repetir exactamente el comando con su clave devuelve la respuesta 201 original, aun después de otras escrituras. Reutilizar la clave con otra solicitud, con el identificador de importación o crear un ID ya existente produce 409. Un conflicto concurrente requiere repetir el comando completo con la misma clave; no generar un ID nuevo para un reintento.

## Avisos en tiempo real

Hub: `/hubs/finances`. Usa el mismo token de sesión validado por el proveedor actual. Cada conexión se asocia al UUID autenticado; el hub no permite elegir otro propietario ni unirse a grupos arbitrarios.

Evento: `FinanceChanged` con `{ eventId: "UUID", revision: "2" }`. Es una señal para consultar nuevamente `GET /api/v2/finances`, no un historial incremental. No incluye importes, datos de otras cuentas ni tokens.

El worker consulta la outbox cada segundo en lotes de hasta 100 eventos. Publica después del commit y marca el evento después del envío. Un fallo conserva el evento para reintentar. Puede haber entregas duplicadas; el cliente debe comparar revisiones, tolerar duplicados y consultar también al reconectar, recuperar foco y volver del segundo plano. Una entrega sin clientes conectados no se reproduce después: la consulta al reconectar recupera el estado.

Los clientes SignalR deben usar `accessTokenFactory` para obtener un token vigente. Los transportes WebSocket/SSE del navegador pueden enviarlo en `access_token`; la API lo acepta solo en GET del hub, no en endpoints financieros. Las conexiones se cierran cuando vence su autenticación. Los orígenes del navegador se limitan a `Cors:Origins`; añade el origen de la futura web antes de conectarla. Las peticiones generales no registran su URL completa para evitar guardar el token del transporte. Configura también el proxy/hosting para no registrar esos parámetros.

Esta implementación entrega a conexiones de **una instancia de API**. Antes de escalar a varias réplicas, configurar un backplane o servicio SignalR compartido; de otro modo, una instancia puede marcar como enviado un evento mientras el cliente está conectado a otra. La outbox no sustituye ese transporte compartido.

## Validación

`npm run api:test` verifica migraciones, importación, comandos, aislamiento, idempotencia, concurrencia, conservación del original, entrega/reintentos de outbox y protocolo WebSocket. Las pruebas de autenticación usan un proveedor HTTP ficticio o el esquema de pruebas; los endpoints reales conservan el proveedor existente. No certifican OAuth con cuentas reales ni concurrencia contra PostgreSQL.
