# API v2: primera etapa implementada

Esta entrega implementa persistencia normalizada e importación/lectura. Todavía no implementa creación/edición de movimientos v2, comandos de bolsillos, SignalR ni clientes nuevos. No se ha migrado ninguna cuenta real.

## Tablas y migración

`Financia.Api/Persistence/` contiene `NormalizedFinanceDb`, las entidades y la migración `20261113000100_InitialNormalized`. Se crean `finance_accounts`, `pockets` y `movements` en el esquema PostgreSQL `financia`, fuera de `public`. El esquema debe permanecer fuera de los esquemas expuestos por la Data API. Las credenciales de base de datos pertenecen al backend; los clientes solo usan tokens de usuario.

Las claves de bolsillos y movimientos incluyen el usuario. Se mantienen IDs originales y dos decimales de precisión. La tabla `Documents` se consulta para importar el historial del servidor, pero no forma parte de las migraciones v2. El historial de migraciones v2 usa una tabla independiente `__FinanciaV2MigrationsHistory`.

SQLite permite las pruebas locales. PostgreSQL necesita además validación de integración en un servidor real antes del despliegue: las pruebas de generación SQL no sustituyen esa comprobación.

## Ejecutar en una base aislada

Desde la raíz, para una copia de desarrollo nueva, configura una ruta distinta de tu base habitual:

```powershell
$env:ConnectionStrings__Postgres = ''
$env:ConnectionStrings__Sqlite = 'Data Source=financia-v2-dev.db'
$env:FinanceV2__Enabled = 'true'
npm run api:start
```

En desarrollo, se inicializa primero la tabla v1 y se aplican después las migraciones v2. En producción las migraciones son explícitas. En una base nueva inicializa primero v1 con `npm run api:start -- -- --initialize-database`; después, con la bandera v2 activa, ejecuta `npm run api:start -- -- --migrate-v2`. En una base que ya contiene `Documents`, basta el segundo comando. Estos comandos actúan contra la conexión configurada: probar siempre primero con una copia aislada.

La bandera es para introducir esta etapa en un entorno controlado. Mantén todas las instancias con la misma configuración y detén instancias antiguas antes de importar. Si desactivas v2 después de importar cuentas, los endpoints v2 dejan de estar disponibles pero v1 sigue bloqueando esas cuentas al detectar las tablas normalizadas. La reversión requiere reconciliar datos, no cambiar la bandera.

No importes una cuenta utilizada por la app actual hasta que su cliente v2 esté disponible: tras importar, los endpoints v1 devuelven 409 para esa cuenta.

## Autenticación y endpoints

Usan el mismo Bearer token de Supabase ya validado por la API. El usuario siempre se obtiene de la sesión. No hay un parámetro para elegir otro propietario.

- `GET /api/v2/finances`: devuelve `{ revision: "0", snapshot: { version: 2, transactions: [], pockets: [] } }` si no se ha importado la cuenta. Después de importar, la revisión inicial es `"1"`.
- `POST /api/v2/imports/legacy`: importación atómica y explícita. Requiere `Idempotency-Key` (máximo 128 caracteres) y `expectedRevision: "0"`.

Si el usuario ya tiene un historial v1 en el servidor, consulta su revisión con `GET /api/finances` y envía solo:

```json
{ "expectedRevision": "0", "legacyRevision": "1" }
```

El backend toma el snapshot directamente de `Documents`; no lo sustituye por uno enviado por el cliente. Una revisión antigua produce 409. Se conserva el JSON original y su revisión.

Si no existe historial en el servidor, se permite una importación local explícita:

```json
{
  "expectedRevision": "0",
  "snapshot": {
    "version": 1,
    "transactions": [
      { "id": "local-1", "currency": "DOP", "amount": 1250.50, "type": "ingreso", "category": "salario", "date": "2026-11-01T12:00:00Z" }
    ],
    "pockets": []
  }
}
```

Antes de usar este camino, el cliente debe verificar y mostrar a qué cuenta pertenecen los datos locales. El servidor solo puede asignarlos al usuario autenticado; no puede demostrar a quién pertenecía un archivo local.

Repetir la misma solicitud con la misma clave devuelve el resultado de la importación; usar otra clave en una cuenta importada o reutilizar la clave con otro contenido produce 409. Este incremento conserva el recibo de la importación en `finance_accounts`; los recibos generales y la outbox se añadirán con las futuras operaciones de escritura.

Los montos de la **respuesta v2** son cadenas decimales (`"1250.50"`), y las versiones y revisiones son cadenas enteras. La entrada legacy mantiene números por compatibilidad. Las fechas deben tener zona horaria explícita y se normalizan a UTC.

Se conservan los saldos existentes sin recalcularlos. Los bolsillos admiten el `color` local opcional. Las referencias a bolsillos históricos ausentes se rechazan con 400 y una lista `movementIds`; requieren resolver la representación histórica antes de importar. No se descarta ni reclasifica el historial.

400 indica datos inválidos, 401 sesión inválida, 409 conflicto/revisión antigua. Los fallos de concurrencia devuelven 409 para recargar y reintentar. Importación y escrituras v1 usan transacciones serializables cuando v2 está activa para evitar que ambas fuentes diverjan.

## Validación

`npm run api:test` verifica migraciones, importación, aislamiento, idempotencia, conservación del original, rechazo de datos inconsistentes y compatibilidad v1. La autenticación se sustituye únicamente en los tests; los endpoints reales conservan el proveedor existente.
